Build an MCP Server with Node.js & TypeScript: Complete Guide

The Model Context Protocol (MCP) transforms how AI models interact with private systems, tools, and databases. Build a production-grade MCP server in Node.js and TypeScript with verified SDK patterns, schema validation, and security boundaries.

By Abubakkar Sajid · Full Stack Developer

Integrating large language models with internal databases, corporate knowledge repositories, and operational APIs used to require custom glue code for every agent platform. Anthropic introduced the Model Context Protocol (MCP) as an open, standardized bridge between AI clients and local or remote data providers. With MCP, you write an integration once as an MCP server, and any compliant host—such as Claude Desktop, Cursor, IDE assistants, or custom enterprise agents—can discover, inspect, and invoke your tools and resources securely.

In this comprehensive guide, we will build a production-ready MCP server using Node.js and TypeScript. We will cover the core architecture, initialize a typed project, implement tools with Zod schema validation, expose dynamic and static resources, connect to clients via standard input/output (stdio) and Server-Sent Events (SSE), test locally with the official MCP Inspector, and enforce strict security boundaries. If you are building AI agents, this guide pairs naturally with our breakdown of production AI agent architecture and our core Node.js API security best practices.

Understanding the Model Context Protocol Architecture

MCP operates as a client-host-server protocol built on JSON-RPC 2.0. Rather than letting an LLM execute arbitrary code against your backend, the protocol formalizes a clear capability contract:

  • MCP Hosts: The application initiating AI tasks, such as Claude Desktop, Cursor, VS Code, or an internal agent runtime. The host controls security policies and user permissions.
  • MCP Clients: Protocol endpoints maintained inside the host application. A single host can connect to multiple MCP clients simultaneously, with each client managing a 1:1 connection to an MCP server.
  • MCP Servers: Lightweight services that expose capabilities through three standardized primitives: Tools, Resources, and Prompts.

The protocol defines three core primitives that servers can expose to clients:

  1. Tools: Executable functions that allow the model to perform stateful operations or fetch dynamic information (e.g., executing a database query, fetching a customer record, or triggering an API webhook). Tools require parameter validation and explicitly return text or binary results.
  2. Resources: File-like data streams that provide read-only context to the model. Resources are identified by custom URIs (e.g., postgres://tenants/42/schema or file:///logs/app.log) and can be subscribed to for real-time updates.
  3. Prompts: Pre-packaged, parameterized prompt templates that guide users and models through specific domain workflows.

For communication, MCP supports two official transport layers: stdio (standard input/output), ideal for local utilities spawned as sub-processes by desktop clients, and SSE (Server-Sent Events over HTTP), designed for remote, networked microservices running on cloud infrastructure. For background on building robust HTTP endpoints, refer to our RESTful API design guide.

Setting Up the TypeScript Project

Let us set up a clean, modern Node.js project using ES modules and TypeScript. Create a new directory and initialize your configuration:

mkdir mcp-server-node && cd mcp-server-node
npm init -y
npm install @modelcontextprotocol/sdk zod
npm install -D typescript @types/node tsx

Configure your tsconfig.json to ensure strict typing, NodeNext module resolution, and clean build output:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "lib": ["ES2022"],
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"]
}

Update your package.json to declare "type": "module" and add build and runtime execution scripts:

{
  "name": "mcp-server-node",
  "version": "1.0.0",
  "type": "module",
  "main": "dist/index.js",
  "bin": {
    "mcp-server-node": "dist/index.js"
  },
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js",
    "dev": "tsx src/index.ts"
  }
}

Implementing an MCP Server with the Official SDK

The official @modelcontextprotocol/sdk provides both low-level protocol handlers and an ergonomic high-level McpServer abstraction. In modern implementations, McpServer is preferred because it integrates directly with Zod for automatic parameter schema generation and runtime validation.

Let us create our server entry point at src/index.ts. We will configure standard input/output transport, register custom tools with strict type boundaries, and expose contextual resources:

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

// Initialize the MCP Server instance with name and version metadata
const server = new McpServer({
  name: "enterprise-support-mcp",
  version: "1.0.0"
});

// Mock database simulating customer and order records
const mockOrders = new Map([
  ["ORD-101", { id: "ORD-101", customerId: "CUST-9", status: "shipped", total: 129.50 }],
  ["ORD-102", { id: "ORD-102", customerId: "CUST-4", status: "processing", total: 49.00 }]
]);

// 1. Register an actionable Tool with Zod validation
server.tool(
  "getOrderDetails",
  "Retrieve comprehensive status and line items for a specific order by ID",
  {
    orderId: z.string().regex(/^ORD-\d{3,}$/, "Order ID must match format ORD-XXX")
  },
  async ({ orderId }) => {
    const order = mockOrders.get(orderId);
    
    if (!order) {
      return {
        isError: true,
        content: [
          {
            type: "text",
            text: `Error: Order with ID '${orderId}' was not found in the database.`
          }
        ]
      };
    }

    return {
      content: [
        {
          type: "text",
          text: JSON.stringify(order, null, 2)
        }
      ]
    };
  }
);

// 2. Register an administrative Tool with business logic
server.tool(
  "cancelOrder",
  "Cancel an unfulfilled order and initiate a payment refund",
  {
    orderId: z.string(),
    reason: z.string().min(5, "A descriptive cancellation reason is required")
  },
  async ({ orderId, reason }) => {
    const order = mockOrders.get(orderId);
    if (!order) {
      return {
        isError: true,
        content: [{ type: "text", text: `Order ${orderId} does not exist.` }]
      };
    }

    if (order.status === "shipped") {
      return {
        isError: true,
        content: [{ type: "text", text: `Cannot cancel order ${orderId}: order has already shipped.` }]
      };
    }

    order.status = "cancelled";
    return {
      content: [
        {
          type: "text",
          text: `Order ${orderId} successfully cancelled. Reason logged: "${reason}".`
        }
      ]
    };
  }
);

// 3. Expose a static Resource for operational guidelines
server.resource(
  "cancellationPolicy",
  "policy://cancellations",
  async (uri) => ({
    contents: [
      {
        uri: uri.href,
        text: "Policy: Orders can only be cancelled prior to dispatch. Shipped orders require standard return authorization.",
        mimeType: "text/plain"
      }
    ]
  })
);

// Start the server using Stdio transport
async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  // Log strictly to stderr: stdout is reserved exclusively for JSON-RPC messages!
  console.error("Enterprise Support MCP Server running on stdio");
}

main().catch((err) => {
  console.error("Fatal server error:", err);
  process.exit(1);
});

Notice the critical rule of stdio MCP servers: never write debug statements or random logs to console.log(). In stdio mode, standard output is the dedicated communication channel for JSON-RPC framing. Any unformatted text sent to stdout corrupts the protocol stream and causes the host client to terminate the session. Always direct diagnostics, operational traces, and error messages to console.error().

Creating and Validating Complex Tools

Tools are the primary mechanism through which AI agents affect real-world outcomes. To make tools resilient in production, observe three foundational practices:

1. Descriptive Schemas and Tool Prompts

LLMs use tool descriptions and parameter metadata to decide when and how to call your functions. Vague descriptions lead to tool hallucination or missed invocations. Write explicit descriptions specifying constraints, formats, and side effects.

2. Strict Input Validation with Zod

Never trust LLM parameters to be well-formed. Use Zod primitives such as .regex(), .email(), .min(), .max(), and enum restrictions. When validation fails, Zod surfaces helpful validation errors back to the model, allowing the LLM to self-correct its arguments on the subsequent turn.

3. Graceful Error Signaling

When a business validation fails (e.g., an order is already cancelled or an entity ID does not exist), do not let an unhandled exception crash the server process. Return an object with isError: true and a descriptive message. This informs the model of the domain failure while preserving protocol stability.

Connecting Your Server to AI Clients

Once your server is built, you can connect it to compatible hosts. Let us examine two major connection targets: desktop clients via stdio, and remote clients via SSE.

Connecting to Claude Desktop

Claude Desktop reads MCP configurations from its configuration file. Open your configuration:

  • macOS: ~/Library/Application Support/Claude/claude_desktop_config.json
  • Windows: %APPDATA%\Claude\claude_desktop_config.json

Add your server under the mcpServers dictionary. Make sure to supply the absolute path to your node binary and compiled script:

{
  "mcpServers": {
    "enterprise-support": {
      "command": "node",
      "args": ["/absolute/path/to/mcp-server-node/dist/index.js"],
      "env": {
        "NODE_ENV": "production",
        "DATABASE_URL": "postgresql://user:password@localhost:5432/orders"
      }
    }
  }
}

Restart Claude Desktop. A hammer icon appears in the interface, displaying your exposed tools: getOrderDetails and cancelOrder. Claude can now query your local database when answering customer questions.

Local Development and Debugging with MCP Inspector

Testing an MCP server by repeatedly prompting a desktop LLM is slow and imprecise. The MCP team provides an interactive, browser-based diagnostic harness: the MCP Inspector. It lets you inspect capabilities, invoke tools manually with custom JSON payloads, view resource contents, and inspect raw JSON-RPC traffic.

Run the inspector directly with npx against your development script:

npx @modelcontextprotocol/inspector node dist/index.js

The inspector starts a local web dashboard (typically at http://localhost:5173). In the UI, you can click on any registered tool, enter mock parameters, and view the raw output and error envelopes in real time. This workflow allows you to verify database connections, mock third-party failures, and test edge cases before introducing model unpredictability.

Remote MCP: Deploying with Server-Sent Events (SSE)

While stdio is perfect for local developer machines, distributed teams and production AI agents require centralized, cloud-hosted MCP servers. For remote scenarios, the SDK provides SSEServerTransport over standard HTTP.

Here is an example configuring an Express server with an SSE endpoint for streaming responses and a companion POST endpoint for receiving JSON-RPC messages:

import express from "express";
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { SSEServerTransport } from "@modelcontextprotocol/sdk/server/sse.js";

const app = express();
const server = new McpServer({
  name: "remote-enterprise-mcp",
  version: "1.0.0"
});

// Store active client transports by session ID
const transports = new Map<string, SSEServerTransport>();

// SSE endpoint: AI clients initiate a long-lived GET request here
app.get("/sse", async (req, res) => {
  // Enforce API key or Bearer token authorization
  const authHeader = req.headers.authorization;
  if (!authHeader || authHeader !== `Bearer ${process.env.MCP_AUTH_SECRET}`) {
    res.status(401).send("Unauthorized: Invalid MCP bearer token");
    return;
  }

  const transport = new SSEServerTransport("/messages", res);
  const sessionId = transport.sessionId;
  transports.set(sessionId, transport);

  res.on("close", () => {
    transports.delete(sessionId);
  });

  await server.connect(transport);
});

// Messages endpoint: AI clients send JSON-RPC command payloads here
app.post("/messages", express.json(), async (req, res) => {
  const sessionId = req.query.sessionId as string;
  const transport = transports.get(sessionId);

  if (!transport) {
    res.status(404).send("Session expired or invalid");
    return;
  }

  await transport.handlePostMessage(req, res);
});

app.listen(3000, () => {
  console.log("Remote MCP server listening on https://api.internal.net/sse");
});

When running over HTTP, always terminate TLS at an authenticated gateway, enforce strict token authorization, and apply rate limiting. For details on protecting long-lived connections and APIs, check out our guide on AI chatbot integrations in Node.js.

Security, Authentication, and Sandboxing

Allowing an autonomous model to call functions on your internal infrastructure carries inherent risk. An attacker could exploit prompt injection to trigger malicious tool calls. Apply these defensive controls:

1. Least-Privilege Execution

Never connect an MCP server using administrative or root database credentials. Create a dedicated database role with restricted permissions limited to specific tables and views. For multi-tenant databases, enforce row-level security as outlined in our guide on multi-tenant PostgreSQL architecture.

2. Confirmation Gates for Destructive Actions

Distinguish between read-only tools (e.g., searching documents or retrieving order status) and state-mutating tools (e.g., issuing refunds, deleting users, or deploying code). For dangerous actions, design your tools to return a signed confirmation token requiring secondary user approval before final execution.

3. Strict Egress and SSRF Filtering

If your MCP server includes tools that fetch external URLs or inspect network resources, strictly block private IP ranges (e.g., 127.0.0.1, 10.0.0.0/8, 169.254.169.254) to prevent Server-Side Request Forgery against cloud metadata services.

Common Pitfalls and Troubleshooting

  • Stdout Pollution: Writing anything other than valid JSON-RPC to standard output in stdio mode breaks the client connection. Use console.error() or a structured file logger for all runtime diagnostics.
  • Process Zombie Leaks: If the parent client process dies abruptly, ensure your server listens for SIGTERM and SIGINT to close active database connections and terminate cleanly.
  • Overly Broad Tool Names: Naming a tool getData or process confuses the LLM's tool selector. Use unambiguous verbs and nouns like fetchCustomerInvoiceHistory or provisionStripeCustomer.
  • Missing Timeout Budgets: If a tool relies on a downstream API, enforce strict timeout limits (e.g., 5 seconds with an AbortController). An unresponsive tool blocks the entire agent loop.

Production Best Practices Checklist

  • Compile TypeScript down to clean ES modules with generated source maps.
  • Validate every single tool argument using Zod schemas with descriptive error messages.
  • Keep all diagnostics on stderr; keep stdout clean for stdio communication.
  • Implement human confirmation or tokenized two-phase commits for irreversible business actions.
  • Test tool schemas and error responses interactively with the MCP Inspector before deployment.

Frequently Asked Questions

What is the difference between MCP and traditional REST APIs?

REST APIs are designed for deterministic client applications following predictable request-response cycles. MCP is designed specifically for AI models: it standardizes dynamic capability discovery, semantic descriptions, file-like resource streams, and prompt templates over a unified JSON-RPC protocol.

Can I run multiple MCP servers inside one client?

Yes. MCP hosts like Claude Desktop or Cursor can connect to dozens of independent MCP servers concurrently. The host aggregates all tools and resources into a single contextual environment for the model.

How do I secure an MCP server deployed over the internet?

When using SSE transport over HTTP, place the server behind an HTTPS reverse proxy, validate bearer tokens or API keys on every connection, enforce IP allowlisting where appropriate, and sandbox internal data access.
