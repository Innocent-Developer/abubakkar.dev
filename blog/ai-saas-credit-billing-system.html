AI SaaS Credit Billing System: Reservations, Usage & Audit History

A durable wallet, atomic reservation protocol and audit ledger for charging AI usage without concurrent overspending or duplicate settlement.

By Abubakkar Sajid · Full Stack Developer

An AI SaaS credit billing system needs a durable wallet, an immutable audit ledger and a request lifecycle: reserve a bounded amount before generation, meter actual provider usage, then settle or release the reservation once. A conditional balance update prevents concurrent overspending; an idempotency key prevents a retried user action from creating a second charge. Credits are a product accounting unit, separate from tokens and money.

This guide retains the original usage-log and centralized pricing ideas, while replacing the earlier request-local “reservation” example with a transactional design. The PostgreSQL schema and SQL protocol below are illustrative architecture examples, not a claim about a particular deployed product. For context, read how SaaS products work and PostgreSQL tenant isolation.

1. Model the credit lifecycle explicitly

  1. Available: credits that can fund new requests.
  2. Reserved: credits held for work already accepted, but not yet finalized.
  3. Captured: credits charged after the final usage calculation.
  4. Released: unused reserved credits returned to the available balance.
  5. Refunded: an explicit correction to a completed charge, linked to its original request.

Keep these states separate. Checking a balance and assigning req.creditReservation does not change durable state: several requests can pass the same check. An atomic increment after the model call also fails to prevent overspending during generation. Reserve first in the database, then call the provider outside the transaction.

Define policy for monthly grants, top-ups, expiry and plan changes. An append-only grant or adjustment event is easier to reconcile than silently resetting a number. If credits expire by purchase batch or grant period, model credit lots and allocation order; a single aggregate wallet cannot answer which credits expired. Do not change the value of credits already purchased without an explicit product policy.

2. PostgreSQL wallet, request and audit schema

Use integers for credit units and small fractional units if the product needs them. Use a decimal or integer microcurrency representation for money; avoid JavaScript floating-point arithmetic in financial calculations. This minimal schema assumes one wallet per user within a tenant. A pooled organization wallet would use a different ownership key.

CREATE TABLE credit_wallets (
  tenant_id uuid NOT NULL,
  user_id uuid NOT NULL,
  available bigint NOT NULL DEFAULT 0 CHECK (available >= 0),
  reserved bigint NOT NULL DEFAULT 0 CHECK (reserved >= 0),
  PRIMARY KEY (tenant_id, user_id)
);

CREATE TABLE usage_requests (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  user_id uuid NOT NULL,
  idempotency_key text NOT NULL,
  request_fingerprint text NOT NULL,
  reserved_credits bigint NOT NULL CHECK (reserved_credits > 0),
  charged_credits bigint CHECK (charged_credits >= 0),
  status text NOT NULL CHECK
    (status IN ('reserved', 'pending_reconciliation', 'settled', 'released')),
  usage_snapshot jsonb,
  price_version text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, user_id, idempotency_key),
  FOREIGN KEY (tenant_id, user_id)
    REFERENCES credit_wallets (tenant_id, user_id)
);

CREATE TABLE credit_events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  request_id uuid NOT NULL REFERENCES usage_requests(id),
  operation_key text NOT NULL UNIQUE,
  event_type text NOT NULL,
  available_delta bigint NOT NULL,
  reserved_delta bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX usage_requests_owner_time
  ON usage_requests (tenant_id, user_id, created_at DESC);

Application code must validate nonempty bounded idempotency keys, request identifiers and credit amounts. A server-generated fingerprint covers the normalized operation, selected model and relevant input. Reusing a key with a different fingerprint is a conflict, not permission to change an in-flight request. Enforce tenant authorization before accessing the wallet or request; opaque UUIDs do not establish ownership.

The example event table covers request-related movements. Add separate, constrained grant/payment records for purchases and monthly allocations. Restrict updates and deletes on audit rows through database roles; “append-only” is an operational invariant, not something a timestamp column guarantees.

3. Reserve credits atomically before the provider call

The following statements form a protocol executed individually on one database connection inside one transaction. Bind each statement?s parameters separately as indicated. Each guard comment is application behavior that must be implemented; running the SQL alone without those branches is incomplete.

BEGIN;

-- Bind: request ID, tenant ID, user ID, key, fingerprint, credits, price version.
INSERT INTO usage_requests
  (id, tenant_id, user_id, idempotency_key, request_fingerprint,
   reserved_credits, status, price_version)
VALUES ($1, $2, $3, $4, $5, $6, 'reserved', $7)
ON CONFLICT (tenant_id, user_id, idempotency_key) DO NOTHING
RETURNING id;
-- If no row was inserted, load the existing authorized request.
-- Compare its fingerprint. Return its stored state; do not generate again.

-- Bind: tenant ID, user ID, credits.
UPDATE credit_wallets
SET available = available - $3, reserved = reserved + $3
WHERE tenant_id = $1 AND user_id = $2 AND available >= $3
RETURNING available, reserved;
-- If no wallet row was updated, ROLLBACK and reject the request.

-- Bind: request ID, credits.
INSERT INTO credit_events
  (request_id, operation_key, event_type, available_delta, reserved_delta)
VALUES ($1, 'reserve:' || $1::text, 'reserve', -$2, $2);

COMMIT;

Validate that the reserved credit amount is a positive bounded integer before entering the transaction. The conditional update serializes competing wallet changes and cannot decrement below zero. The uniqueness constraint handles duplicate submissions. A new request row, wallet movement and audit event must commit together; any failure rolls them all back. Configure lock and statement timeouts, and handle deadlocks or retryable transaction failures with bounded retries.

Only after commit should a worker or request handler invoke the model. Persist a job or outbox entry in the same transaction if work must survive a process crash between reservation and dispatch. A database transaction cannot atomically commit an external model request; account for this gap rather than promising exactly-once provider execution.

4. Settle, release and refund without double charging

To settle a completed generation, start another transaction and lock the authorized request row with SELECT ... FOR UPDATE. If it is already settled, return the stored result. For an eligible reserved request with reservation r and actual charge a, verify 0 ≤ a ≤ r, then apply:

available_delta = r - a
reserved_delta  = -r
request.status  = 'settled'
request.charged_credits = a
event.operation_key = 'settle:' + request.id

Update the wallet, request usage snapshot and unique settlement event together. All paths should lock request then wallet in the same order. The event uniqueness constraint supplements the state check; it does not replace it. PostgreSQL’s row-locking documentation explains how competing transactions wait on these locks.

A definitive failure before billable work can release the reservation with a corresponding ledger event. A timeout is ambiguous: the provider may have completed and charged the operation. Mark it pending reconciliation until provider evidence or a documented policy resolves it. Do not automatically release on every HTTP error and retry indefinitely.

Refunds are new ledger movements, not deletion of the charge. Give each refund a unique operation key and a reference to the original charge. Serialize refund processing and enforce that cumulative refunds cannot exceed the captured amount. Payment refunds, product credit refunds and unused reservation releases are different operations with different reconciliation requirements.

5. Meter actual AI usage and version the conversion

Record provider, model, provider request ID, input/output usage, cached input, embeddings and any separately priced tool calls that apply. Some provider/model combinations also expose reasoning or other usage categories. Use their documented billing fields and avoid counting a category twice if it is already included in a total. Track each attempt separately because retries and tool loops may generate more than one provider charge.

A MongoDB usage-log pattern can be useful for analytics, but a usage log is not a transactional wallet. For example, a Mongoose log can store userId, provider, model, token counts, creditsCharged and createdAt, indexed by user and date. Link it to the durable request ID. If MongoDB is the accounting store, use a conditional update and suitable transactions for the wallet, request and ledger; independently updating Redis and MongoDB is not one atomic operation.

Centralize pricing in a versioned price book with model identifiers, currency, units, effective date and each billed category. A conceptual conversion is:

provider_cost = sum(usage_category × price_per_category_unit)
credits = round_using_published_policy(provider_cost / currency_per_credit)

Choose and document when rounding occurs. Rounding every token category separately can charge more than rounding the aggregate. Use exact integer or decimal arithmetic and store the price version so a past charge remains explainable after prices change. A simple tokens-per-credit ratio can be a product policy, but it does not demonstrate provider margin across models with different input and output prices.

Configuration pitfalls to prevent

  • Reject negative or malformed plan limits at startup rather than silently granting usage.
  • Do not serialize JavaScript Infinity as a quota: JSON turns it into null. Represent plan policy explicitly and retain a finite per-request safety cap.
  • Keep plan configuration immutable; per-user usage belongs in durable records.
  • Define downgrade and expiry rules so remaining balances retain a clear meaning.
  • Never publish a margin table using unsourced rates. Recalculate from current provider invoices and rate cards.

6. Protect the accounting boundary

Clients cannot choose their balance, usage totals, price version or final charge. Resolve tenant membership and plan entitlement server-side. Bound prompt size, output budget, concurrent requests, tool depth and retry count before generation. Apply per-account and per-operation limits in addition to IP controls. The Node.js security checklist covers authorization and resource exhaustion.

Verify payment webhook signatures against the provider’s required payload bytes. Deduplicate events before granting credits, check account mapping and process payment-state changes explicitly. A redirect to a success page is not evidence of a completed payment. Keep provider keys outside client code and redact personal prompts and credentials from logs.

7. Reconcile and test failure paths

  • Submit the same key concurrently and confirm one request and one reservation.
  • Submit distinct requests against the same small balance and confirm no negative balance.
  • Replay settlement and refund events; verify totals stay unchanged.
  • Crash after reservation, dispatch, provider completion and before settlement.
  • Verify that ambiguous timeouts remain discoverable for reconciliation.
  • Compare wallet movement to ledger totals and provider usage; alert on stale holds and mismatches.

Redis may help cache derived balances or enforce a coarse request rate. Keep one authoritative accounting store unless you deliberately design and reconcile a distributed protocol. Back up the ledger and test recovery, including how restored request state relates to provider operations already completed.

Frequently asked questions

Should users pay by requests, tokens or credits?

It depends on the product contract. Credits can abstract varying provider costs, while requests can work for tightly bounded tasks. Meter provider usage either way and make the user-facing charging policy predictable.

How large should a reservation be?

Use a conservative bound based on permitted model, input, output and tool work. If actual usage can exceed it, stop before expanding work or reserve an additional amount atomically. Do not silently create a negative balance.

Does idempotency guarantee only one provider charge?

No. It controls repeated application actions. A crash after provider submission may leave the outcome uncertain; use provider-supported idempotency where available and reconcile ambiguous attempts.
