Build an AI Chatbot with Node.js, OpenAI & Gemini APIs

A production-friendly chatbot keeps provider credentials on the server, validates and bounds user input, stores conversation state deliberately, and treats model output as untrusted data. The adapter pattern below lets a Node.js endpoint call either OpenAI or Gemini without exposing either key to the browser.

By Abubakkar Sajid · Full Stack Developer

This is an illustrative JavaScript example for a Node.js backend. It uses the OpenAI JavaScript SDK’s Responses API and Google’s `@google/genai` SDK. SDKs and available models change, so install current supported releases, select a model available to your account through configuration, and verify behavior in provider documentation before shipping. The snippets demonstrate API shape, not a complete deployable application. For usage accounting, pair this with the AI SaaS credit and billing guide.

1. Keep API keys on the server

Install the official SDKs in a Node project and configure `OPENAI_API_KEY` and `GEMINI_API_KEY` in your local secret manager or deployment platform. Do not place them in frontend code, commit a `.env` file, or include them in error logs. Use separate keys per environment and rotate exposed credentials immediately.

npm install openai @google/genai express

Keep provider setup in a backend module. The client sends a provider choice from an allowlist, while the server decides the actual model name and credentials. Never accept arbitrary model IDs or API base URLs from the request.

2. Put provider differences behind an adapter

A small common function is enough for a first version. It accepts bounded conversation turns and returns text plus normalized usage metadata when available. Provider-specific response shapes stay inside the adapters. A useful follow-up is to make the return type explicit in TypeScript and persist provider request IDs for support.

import OpenAI from 'openai';
import { GoogleGenAI } from '@google/genai';

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });
const gemini = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });

export async function replyWithOpenAI(messages) {
  const response = await openai.responses.create({
    model: process.env.OPENAI_MODEL,
    input: messages.map(({ role, content }) => ({ role, content })),
  });
  return { text: response.output_text, responseId: response.id };
}

export async function replyWithGemini(messages) {
  const response = await gemini.models.generateContent({
    model: process.env.GEMINI_MODEL,
    contents: messages.map(({ role, content }) => ({
      role: role === 'assistant' ? 'model' : 'user',
      parts: [{ text: content }],
    })),
  });
  return { text: response.text ?? '' };
}

Provider conversation roles do not always match exactly. The example maps assistant output to Gemini’s `model` role and uses plain text content. Validate the exact supported input schema for your installed SDK and model, especially when adding tool calls, images, system instructions, or persisted provider state. Do not assume a provider’s raw response is interchangeable with another’s. Check the official OpenAI Node SDK Responses guide and Google’s Gemini content generation reference when upgrading SDKs or model configuration.

3. Validate input and choose the provider safely

Reject invalid provider names, empty prompts, oversized messages, and excessive conversation history before making a paid request. The browser is untrusted: users can replay requests or alter hidden fields. Authenticate the user, check their account’s entitlement and usage limit, then apply per-user and per-IP rate limits.

const providers = {
  openai: replyWithOpenAI,
  gemini: replyWithGemini,
};

app.post('/api/chat', requireUser, async (req, res, next) => {
  try {
    const { provider, messages } = chatRequestSchema.parse(req.body);
    await usage.assertCanGenerate(req.user.id);
    const result = await providers[provider](messages);
    await usage.record({ userId: req.user.id, provider, result });
    res.json({ reply: result.text });
  } catch (error) {
    next(error);
  }
});

`chatRequestSchema` is intentionally a placeholder for your validation library. Enforce maximum body size at the HTTP layer too. The route also needs a request deadline, provider-specific error mapping, and a clear policy for usage-recording failure. If billing is credit-based, reserve or authorize usage before generation and reconcile actual provider usage afterward; define how to handle a provider success followed by a database failure.

4. Decide where conversation history lives

For a short demo, a client can send a limited transcript each turn. For a real product, store messages server-side under a conversation ID that belongs to the authenticated user or tenant. Load only the authorized conversation, trim or summarize old turns, and apply retention and deletion rules. Do not trust a submitted history as proof of what the assistant previously said.

Long context increases latency and cost and can bury important instructions. Set turn and token budgets, define summarization rules, and test whether summaries preserve the facts the product needs. If using retrieval augmented generation, scope retrieval by tenant and filter retrieved text as untrusted context.

Give conversations a server-side contract

A production request should generally contain a conversation identifier, a new user message, and a bounded set of product options—not the complete trusted system prompt or an arbitrary model configuration. The server loads the conversation after checking ownership, appends the user turn, and persists the assistant result only after a successful completion. Use a unique client turn ID or idempotency key so a browser retry does not accidentally create duplicate messages and charges.

Keep system instructions under server control and version them. Record which prompt version and provider alias produced a turn so a behavior regression can be investigated, while avoiding raw prompt logging by default. If users can delete a conversation, propagate deletion to derived summaries and retrieval indexes according to the product’s retention commitments.

5. Treat model output as untrusted

Render chatbot text as text, not raw HTML. Escape output in the frontend and validate structured output against a schema before using it. A model response must not directly authorize payments, change account permissions, or execute arbitrary SQL. Tool calling should map to a narrow server-side allowlist; the model can propose a tool call, but the application validates arguments and authorization before execution.

Do not include secrets or unnecessary personal data in prompts. Consider data retention and provider settings for your use case, and make user-facing privacy statements match actual behavior. Add moderation or domain rules where the product risk calls for them; a system instruction alone is not a security boundary.

Evaluate chatbot behavior before and after changes

Create a small evaluation set from representative user questions, including ambiguous prompts, unsupported requests, hostile instructions embedded in retrieved documents, and cases that should trigger a refusal or handoff. Store expected criteria rather than requiring exact wording: factual grounding, correct tool selection, safe refusal, and useful clarification are better measures than matching one golden sentence. Run the same set when changing the system prompt, retrieval pipeline, provider, or model alias.

For retrieval, include tests where the correct answer is absent and where another tenant has the relevant document. The expected result should be a safe “not found” or clarification, not a confident guess or cross-tenant citation. Review a sample of live conversations only under a documented privacy policy, with access controls and redaction. An LLM judge can help triage but should not be treated as definitive proof of correctness or safety.

Bound model and conversation budgets

Define server-side limits for message count, input length, output tokens, tool calls, and elapsed time. A limit on characters is not identical to a token limit, so use the provider’s supported output budget setting and apply an application cap before calling it. Calculate the maximum work a single user turn can cause, including retrieval, retries, and tool loops. Per-request caps should complement monthly account quotas and concurrency limits.

For a product with several organizations, include tenant identity in usage ledger records and enforce quota updates atomically. The user should receive a clear error when a budget is exhausted, while internal logs retain enough request context for reconciliation. Link provider request IDs to your own conversation-turn ID so support can distinguish a failed call from a repeated client submission.

6. Handle timeouts, retries, and streaming

Set a total request deadline and propagate cancellation when the client disconnects if supported by the installed SDK and server stack. Retry only errors that are transient and safe to retry, with a small bounded attempt count and jitter. A retry can incur another generation charge, so use an idempotency strategy at your application boundary and reconcile provider usage rather than blindly repeating requests.

Streaming can improve perceived responsiveness, but it complicates cancellation, moderation, partial failures, and billing finalization. Start with a complete response path, then add streaming when the product requires it. Flush chunks using a documented protocol, handle disconnects, and make sure a half-delivered answer is not recorded as a successful completed turn.

Define a provider fallback policy explicitly. Falling back to another model may change answer quality, output format, privacy terms, and cost; it should not happen silently on every error. If you do use fallback, track the provider actually selected, tell the client whether the request is still in progress, and preserve a single application-level turn identifier across attempts. Do not retry authentication, invalid request, or quota errors as though they were transient network failures.

7. Log carefully and monitor the full path

Record request IDs, selected provider/model alias, duration, status category, and token or usage counters when available. Avoid logging full prompts and completions by default; they may contain credentials or personal data. Alert on sustained provider failures, timeouts, budget threshold breaches, and queue growth. A provider’s own rate limit or incident may be outside your application’s control, so return a useful retry message and define a fallback policy.

Keep user-facing errors distinct from internal diagnostics. Return a correlation ID and a stable code such as “generation temporarily unavailable,” then log the provider status and request identifier without secrets. Monitor end-to-end latency separately from provider latency so slow database authorization or retrieval is not mistaken for model performance. Track cancellation and incomplete generations to understand the cost and experience of client disconnects.

8. Test providers without calling them in every test

  • Unit-test provider adapters using representative response shapes and error classes.
  • Test request validation, user authorization, tenant access, and usage limits locally.
  • Test timeout, 429, 5xx, malformed response, and client disconnect behavior with controlled stand-ins.
  • Keep a small opt-in live smoke check for credentials, model access, and current provider behavior.

Mock tests establish your application’s handling of the scenarios you configured; they do not prove current provider availability or billing semantics. Verify those with provider docs and controlled live checks. The API security guide covers additional controls around user input and secrets.

Common chatbot integration mistakes

  • Calling model APIs directly from the browser and exposing a reusable secret.
  • Accepting an arbitrary provider, model, URL, or system instruction from the client.
  • Sending unbounded chat history on every turn.
  • Retrying paid requests without tracking duplicate work or billing effects.
  • Rendering markdown or HTML without sanitization.
  • Assuming a model’s answer is factually correct or safe to execute.

Frequently asked questions

Can one endpoint support both OpenAI and Gemini?

Yes. Keep a stable application request shape and implement a separate adapter for each provider. Normalize only the concepts your product needs; provider-specific features may not map one-to-one.

Should I let users choose a model?

Only from an explicit server-side allowlist and after considering access, safety, and cost. Map public choices to server configuration instead of accepting arbitrary model identifiers.

How do I keep chatbot costs predictable?

Bound input and output, limit turns, rate limit accounts, track provider usage, and enforce product quotas before generation. Review credit-based AI billing patterns for reservation and reconciliation concerns.
