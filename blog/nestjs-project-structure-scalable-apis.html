NestJS Project Structure for Scalable APIs: A Production Guide

A scalable NestJS repository groups code around business capabilities, keeps HTTP concerns at the edge, and makes persistence and external services explicit dependencies. Start with a modular monolith; split deployment only when there is a concrete operational reason.

By Abubakkar Sajid · Full Stack Developer

NestJS gives you modules, controllers, providers, dependency injection, and an opinionated application lifecycle. It does not decide your domain boundaries. A good structure makes it easy to find a feature, test its rules without booting the entire server, and change database or transport details without rewriting business policy. This guide assumes a TypeScript API using the standard Nest application model; adapt filenames to your team’s conventions. For foundational HTTP design, see REST API design, and compare runtime choices in FastAPI vs Node.js.

Start with a modular monolith

A single deployable application with clear internal modules is often the simplest system that scales organizationally. It preserves straightforward local development and transactions while allowing teams to own distinct areas. Microservices add network failures, deployment coordination, observability, and data ownership constraints; they are not a folder layout upgrade.

src/
  main.ts
  app.module.ts
  common/                 # shared infrastructure, not a domain dumping ground
  config/
  database/
  modules/
    accounts/
      accounts.module.ts
      accounts.controller.ts
      accounts.service.ts
      dto/
      domain/
      persistence/
      accounts.service.spec.ts
    projects/
    billing/
  health/
test/

Feature folders are easier to navigate than global `controllers/`, `services/`, and `dto/` folders once the application has several domains. Keep shared code small: promote a utility only after more than one feature needs the same stable behavior. An unbounded `common/` folder often hides the real dependency graph.

Define what belongs in each layer

Modules compose; controllers translate

A Nest module declares providers and imports the modules it depends on. A controller maps HTTP input to application operations and maps outcomes to HTTP responses. Keep controllers thin: parse route parameters, invoke an application service, and choose transport status codes. Avoid putting transactions, authorization rules, and multi-step business decisions in controllers.

Application services express use cases

Use providers for coherent operations such as `CreateProject`, `InviteMember`, or `CancelSubscription`. They coordinate domain rules, persistence ports, and external integrations. Do not create a generic service that mirrors every ORM method; that layer adds indirection without clarifying behavior.

Domain logic should not depend on Nest

When rules are meaningful and likely to be tested independently, keep them in plain TypeScript types and functions. They should not import decorators, HTTP request objects, or ORM models. This boundary is useful, but do not turn every data structure into an elaborate domain-driven design hierarchy.

Persistence owns queries and mapping

Repositories or focused persistence providers translate application needs into database operations. Use explicit methods such as `findVisibleProject(actor, id)` if that makes authorization and visibility part of the query. Avoid returning ORM entities directly as public API responses: map to response DTOs and prevent accidental leakage of fields.

Keep dependency direction visible

Prefer inward calls: controllers call use cases; use cases depend on domain rules and explicit ports; infrastructure implements ports. For smaller systems, a service can inject a concrete repository directly. Introduce an interface token when you need a meaningful seam, such as swapping a provider, isolating a complex external boundary, or testing policy without network and database setup. Abstractions that merely duplicate one implementation add maintenance cost.

// projects.module.ts: feature composition boundary
@Module({
  imports: [DatabaseModule, AccountsModule],
  controllers: [ProjectsController],
  providers: [ProjectsService, ProjectsRepository],
  exports: [ProjectsService],
})
export class ProjectsModule {}

Export only providers other modules actually need. If everything is exported, modules become labels rather than boundaries. Avoid circular imports as a signal to reconsider ownership; `forwardRef()` can resolve a framework wiring cycle, but persistent mutual knowledge usually indicates a domain boundary problem.

Make validation and security cross-cutting

Use DTOs for external request shapes and configure validation globally so endpoints do not silently skip checks. A common Nest setup uses `ValidationPipe` with transformation and a whitelist; whether to reject non-whitelisted fields should be a deliberate API contract choice. Ensure nested DTOs and arrays are validated as well. DTO validation checks input shape, while authorization belongs at the operation or query boundary.

// main.ts, illustrative global validation policy
app.useGlobalPipes(new ValidationPipe({
  transform: true,
  whitelist: true,
  forbidNonWhitelisted: true,
}));

Keep authentication guards and role checks consistent, but do not treat a role such as `user` as permission to access every record. Check ownership or membership for each object. Put secrets in deployment configuration, constrain outbound calls with timeouts, and use a shared rate limit store across replicas. The broader Node.js API security checklist covers those controls.

Configuration, errors, and observability

Load and validate environment configuration once at startup. Fail fast when a required database URL or signing key is missing; do not substitute a production default. Keep provider-specific configuration near its adapter, while centralizing validation and secret injection. Return consistent client errors and use exception filters only when they add stable mapping; never expose stack traces or database details in production responses.

Attach a request or trace identifier to logs, measure latency and error rates by route without logging secrets, and expose readiness separately from liveness. A readiness endpoint should reflect whether the instance can serve meaningful work, not just whether the event loop is alive. Avoid high-cardinality metric labels such as raw user IDs.

Test at the boundary that matters

  • Unit-test deterministic domain rules and application decisions.
  • Test controllers or HTTP paths for validation, guards, status codes, and serialization.
  • Use integration tests for repositories and migrations against a real compatible database.
  • Stub external provider boundaries for retry and timeout policy, then keep a small set of contract checks.

Test authorization failures explicitly: a logged-in caller from one organization must not read another organization’s record. Mocking every provider can make tests fast but may hide ORM behavior; running everything end-to-end makes failures harder to localize.

How to evolve the layout

Add a module when there is a capability with its own rules, data ownership, or lifecycle. Add a queue boundary when work can be asynchronous and the product can represent pending or failed work. Split a service when independent deployment, scaling, regulatory isolation, or team ownership outweighs the cost of network coordination. Keep the migration incremental: extract a clear module, define its API, and observe dependencies before moving it out of process.

Organize shared infrastructure without creating a dependency knot

Put database connection setup, structured logging, and validated configuration in infrastructure modules with clear exports. Feature modules should depend on the narrow provider they use rather than importing the whole application module. Avoid injecting the HTTP request into low-level providers just to discover the current user; pass the actor and tenant explicitly to the operation so the dependency is visible and background jobs can call the same logic.

For request-scoped state such as correlation IDs, use a deliberate request context mechanism and understand the lifecycle implications. Request-scoped providers can propagate scope through dependent providers and add overhead; they are not a replacement for explicit business arguments. Keep context limited to cross-cutting metadata and do not make security-critical tenant access invisible.

Handle transactions and external side effects deliberately

When a use case changes multiple rows, its transaction boundary should be visible in the application operation or a unit-of-work abstraction. Avoid opening a transaction in a controller and passing a raw ORM manager through unrelated modules. If the transaction also needs to send an email or publish an event, remember the database commit and external send cannot usually be atomic together. An outbox table or retryable job can prevent lost notifications, while idempotency keys protect duplicate processing.

Do not keep a database transaction open while waiting on a slow model API or payment provider. Persist an intermediate state, enqueue work, and represent pending or failed outcomes to the client when the task may outlive an HTTP request. A queue processor should be independently testable and should carry explicit tenant and actor context where needed.

Version contracts and generate useful API documentation

Choose a versioning policy before clients depend on unstable shapes. NestJS supports URI, header, and media-type versioning; the right option depends on clients and infrastructure. Keep request DTOs and response models tied to the feature that owns the contract. When generating OpenAPI documentation, verify that examples and auth requirements match the deployed routes. Generated docs are a contract artifact, not proof that authorization or runtime behavior works.

For breaking changes, prefer additive migration where possible: introduce a new field or endpoint, support old and new clients during the transition, then remove obsolete behavior after usage and communication are handled. Keep error codes stable enough for clients to recover without parsing human-readable messages.

Make code ownership clear as the application grows

A module boundary is useful when an engineer can answer three questions quickly: which feature owns this behavior, which providers may it call, and which tests verify its public behavior? A short README for a complex module can record invariants, external dependencies, and migration notes. Avoid maintaining a separate architecture diagram that no longer matches the imports; dependency rules enforced in code are stronger than documentation alone.

Organize tests next to the behavior when that helps navigation, or keep a centralized test directory if the team needs it. The key is predictable placement. Name tests after observable behavior rather than implementation details so refactoring a provider does not require renaming every test.

Global modules are convenient for configuration and logging, but they hide dependencies and make isolated testing harder. Prefer an explicit import in the module that needs a provider unless the dependency is truly universal and stable. Dynamic modules are useful when reusable infrastructure needs caller-supplied options; do not use them to make ordinary feature configuration harder to trace. A developer should be able to follow an injected provider from a feature module without searching through runtime magic.

When a feature owns a public API but shares a core rule with another feature, expose a narrow application operation instead of exporting internal repositories. That keeps each module free to change its persistence details. For example, a billing feature may ask an accounts capability whether a tenant is active, but it should not query another module’s private tables directly. These boundaries also make later extraction possible if evidence supports running the capability separately.

Common NestJS structure mistakes

  • One global `AppService` that accumulates unrelated behavior.
  • A `common` module imported by every feature and then changed without ownership.
  • Controllers calling repositories directly, bypassing authorization and use-case rules.
  • Leaking ORM entities and internal exception messages into API responses.
  • Creating interfaces for every provider before a real substitution or test seam exists.
  • Splitting into microservices to compensate for unclear module ownership.

Frequently asked questions

Should each feature have its own module?

Usually, if it owns a cohesive capability or dependency set. Tiny CRUD endpoints can share a module when they genuinely belong together. Reorganize around change and ownership, not a fixed module count.

Should I use clean architecture with NestJS?

Use its dependency-direction ideas where they protect valuable business rules or external boundaries. A small CRUD application may need only modules, services, DTOs, and repositories. Let complexity justify additional layers.

Where should shared DTOs go?

Keep request and response contracts with the owning feature. Share a type only when it is a real cross-feature contract; a shared folder can otherwise couple otherwise independent endpoints.
