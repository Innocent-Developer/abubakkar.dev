Multi-Tenant SaaS Architecture with PostgreSQL: Complete Guide

For many SaaS products, a shared PostgreSQL database with a shared schema and explicit `tenant_id` is a practical starting point. Enforce tenant ownership in application queries and database constraints, and consider row-level security as defense in depth. Choose stronger physical isolation when customer risk, regulation, or workload requirements justify its operational cost.

By Abubakkar Sajid · Full Stack Developer

Multi-tenancy means one product serves multiple customer organizations while keeping their data and operations isolated. Tenant isolation is a security invariant: a user from organization A must not read, mutate, infer, or export organization B’s records. It affects schema design, API authorization, background jobs, caches, file storage, analytics, and support tooling. This article focuses on PostgreSQL’s shared-schema pattern and the trade-offs around it. For the broader product model, see the SaaS guide; for credit and usage accounting, see the AI SaaS billing design.

Choose an isolation model deliberately

Common storage layouts and their operational trade-offs.
ModelAdvantagesCosts and limits
Shared tables, tenant keySimple migrations, pooled capacity, low operational overhead.Every query path must preserve tenant scope; noisy-neighbor and backup isolation are shared.
Schema per tenantSome namespace separation and tenant-specific restore workflows.Migration and connection management complexity grows with tenant count.
Database per tenantStronger resource and administrative separation; targeted restore is clearer.More provisioning, monitoring, migrations, connection pools, and cost.

These are not immutable tiers. A common path is to start with shared tables, then move selected high-isolation or high-volume tenants to dedicated databases while retaining one application contract. Design migrations and routing with that possibility in mind, but do not build a sharding system before the product needs one.

Model tenant ownership in keys and relationships

Store tenant identity on every tenant-owned row. Make it part of unique constraints and foreign keys so the database rejects cross-tenant relationships, not just the application. Consider globally unique IDs convenient, but they do not enforce tenant isolation by themselves.

CREATE TABLE projects (
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  id uuid NOT NULL,
  name text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id)
);

CREATE TABLE tasks (
  tenant_id uuid NOT NULL,
  id uuid NOT NULL,
  project_id uuid NOT NULL,
  title text NOT NULL,
  PRIMARY KEY (tenant_id, id),
  FOREIGN KEY (tenant_id, project_id)
    REFERENCES projects (tenant_id, id)
);

The composite foreign key prevents a task for one tenant from pointing to another tenant’s project. Create indexes that match actual access paths, often beginning with `tenant_id`; validate plans on production-shaped data. Unique email or slug constraints need a product decision: global uniqueness or uniqueness within a tenant. If per-tenant, include `tenant_id` in the unique index.

Carry tenant context from a trusted source

Resolve the tenant from a verified membership or API credential after authenticating the principal. A request body field like `tenantId` is a selection request, not proof of access. When users can switch organizations, verify membership and role on each context change. Jobs and scheduled tasks should carry an explicit tenant identifier in a validated job payload instead of relying on request-local state.

Make repository APIs tenant-aware so callers have to provide the scope:

async function findProjectForMember(actorId, tenantId, projectId) {
  return db.query(
    `SELECT p.id, p.name
       FROM projects p
       JOIN memberships m ON m.tenant_id = p.tenant_id
      WHERE p.tenant_id = $1 AND p.id = $2
        AND m.user_id = $3 AND m.status = 'active'`,
    [tenantId, projectId, actorId]
  );
}

Use bound parameters. Avoid APIs such as `findById(id)` for tenant-owned data unless the tenant is added inside the repository. Prefer tests asserting that a valid ID from another tenant returns no record, even when the caller is authenticated.

Use PostgreSQL row-level security as a second boundary

Row-level security (RLS) policies can make PostgreSQL filter or reject rows according to a session setting. They are valuable defense in depth against an omitted tenant predicate, but require careful database roles and connection handling. The application role should not own protected tables or have `BYPASSRLS`. Table owners generally bypass policies unless `FORCE ROW LEVEL SECURITY` is enabled. Check the official PostgreSQL row security documentation for the behavior and role exceptions in the version you deploy.

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE ROW LEVEL SECURITY;

CREATE POLICY projects_tenant_policy ON projects
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);

Set tenant context transaction-locally on the same checked-out connection that runs the query. With a pool, never set a session-wide value and return the connection without clearing it. A transaction-local setting resets at transaction end:

await client.query('BEGIN');
try {
  await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
  const result = await client.query(
    'SELECT id, name FROM projects WHERE id = $1', [projectId]
  );
  await client.query('COMMIT');
  return result.rows[0] ?? null;
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}

RLS is not protection against a fully compromised application role that can choose any tenant setting, nor does it replace membership checks. Treat tenant context as trusted only after application authorization, prevent SQL injection, and test with the same non-owner role used in production. Test missing context, transaction rollback, pooled connection reuse, and background jobs. Review the API security checklist alongside the database policy.

Cover data outside ordinary SQL queries

Cache keys

Include tenant identity in cache keys for tenant-scoped objects. A cache key of `project:123` is unsafe if IDs are not guaranteed globally unique or authorization differs by tenant. Invalidate the tenant-specific key after updates.

Files and object storage

Authorize before generating a signed download or upload URL. Use tenant-scoped object keys and short expirations, and avoid exposing storage bucket paths as access control. Apply lifecycle and deletion policies to exports and attachments.

Search, analytics, and logs

Apply tenant filters to search indexes and analytics queries. Restrict support impersonation and administrative exports, record access, and avoid sending sensitive tenant content to third-party telemetry. Backups are shared in a shared database; document restore boundaries and test how a single-customer recovery would work.

Represent membership and roles as tenant-scoped data

Users and organizations have a many-to-many relationship in most SaaS products. Store membership explicitly with a unique constraint on `(tenant_id, user_id)` and a status such as active, invited, or suspended. Check both membership and action-specific permission. An account-wide `isAdmin` flag is usually too broad when the same person belongs to several customer organizations with different roles.

Invitation tokens should be single-use, time-limited, and tied to the intended organization and email or user identity. When ownership changes, record who made the change and preserve the audit trail. Support staff access should be separately authorized, time-bound where practical, and audited; tenant data being in one database does not make unrestricted internal access acceptable.

Design indexes for tenant-scoped access

Include `tenant_id` in indexes used by common filtered queries, often as the leading column when the query always constrains it. Index shape still depends on selectivity and sort order: for a project list ordered newest-first, an index like `(tenant_id, created_at DESC, id)` may help, but verify with representative data and EXPLAIN (ANALYZE, BUFFERS). Avoid adding every possible index because each one adds write and storage cost.

Use keyset pagination with a stable compound cursor for large tenant datasets. Make the cursor opaque and validate it; do not let a client supply arbitrary SQL order expressions. Apply a per-tenant page-size cap to reduce the impact of a noisy client and return clear continuation semantics.

Plan safe tenant-aware migrations

Adding a non-null tenant key to an existing table needs a data mapping plan. First identify the owner of each existing row, backfill in bounded batches, verify that every row maps to exactly one tenant, then add constraints and switch reads and writes. During a rolling deploy, old and new application versions may run at once; use an expand-and-contract sequence so both understand the transitional schema.

For tenant moves or dedicated database extraction, pause or dual-write only with a reconciliation design. Copy data, verify row counts and checksums, compare application-visible results, switch routing for a small controlled cohort, and retain a rollback path. Keep migrations idempotent where possible and define how long old copies remain before secure deletion.

Balance isolation with operational overhead

Shared tables make pooled compute and product-wide migrations straightforward, but one database outage affects all customers and maintenance windows are shared. Schema-per-tenant can make some exports or restores easier, but a fleet of schemas creates migration fan-out and catalog overhead. Separate databases can reduce blast radius and enable tenant-level sizing, though monitoring, connection limits, backup policy, and migration orchestration become more demanding.

Move toward dedicated storage based on a real requirement, such as customer-managed keys, residency, restore guarantees, or persistent resource contention. Keep a registry mapping tenant to storage location and make the application route through it. Do not expose database names or connection strings to clients.

Transactions, migrations, and noisy neighbors

Keep multi-row business changes in database transactions, and place tenant predicates on every query inside them. Online migrations need an expand-and-contract approach when old and new application versions coexist. Backfill tenant IDs in bounded batches, check for orphan or ambiguous records, add constraints after the data is clean, and monitor lock duration.

A shared database also shares CPU, I/O, connection slots, and locks. Use per-tenant quotas for expensive product operations, query timeouts, pagination limits, and queue backpressure. Track usage by tenant without making tenant IDs high-cardinality metric labels. If a single tenant regularly consumes disproportionate resources, capacity or a dedicated deployment may be justified.

Test isolation as a product guarantee

  • Cross-tenant read, update, delete, export, and relationship creation are denied.
  • Queries use tenant filters and relationships enforce tenant consistency.
  • RLS tests run under the application role, not a table owner.
  • Pool reuse does not retain tenant context after commit, rollback, or error.
  • Queues, scheduled tasks, file access, and caches preserve tenant scope.
  • Migrations and restore procedures are rehearsed on representative data.

Include property-style tests for repository methods that accept a tenant identifier: generate records for two tenants and assert that changing only the actor or requested object cannot cross the boundary. Run at least one test against the real database engine because an in-memory substitute may not implement RLS, transaction-local settings, or composite constraints the same way. Seed the test database using the same least-privilege role as the deployed service.

Test tenant context propagation through the full asynchronous path. A request can enqueue a job that runs minutes later on a different process and database connection. The worker must reload current authorization or use an explicit system capability, carry a tenant ID, and scope every query. Avoid relying on ambient process state, a global variable, or a reused connection to remember which customer initiated the work.

Frequently asked questions

Is row-level security enough on its own?

No. It reduces the chance that an omitted predicate leaks rows, but application authorization, least-privilege roles, safe SQL, tenant-aware jobs, and tests remain necessary.

Should every customer have a separate database?

Only when the isolation, compliance, restore, or workload needs justify the added operational work. Shared tables are a sound starting point for many products if tenant boundaries are explicit and tested.

Can I migrate from shared to dedicated tenants later?

Yes, if tenant identity and data access are consistently modeled. Keep tenant routing behind a repository or connection provider and plan migration, verification, rollback, and ownership steps.
