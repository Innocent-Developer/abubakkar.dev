Reliable Webhooks in Node.js: Retries, Queues & Idempotency

Webhooks are the backbone of event-driven architectures, yet naive endpoints regularly drop events, double-charge customers, or crash under retry storms. Master production webhook ingestion in Node.js with raw signature verification, BullMQ background queues, and strict PostgreSQL idempotency.

By Abubakkar Sajid · Full Stack Developer

In modern cloud systems, webhooks are the primary mechanism for asynchronous inter-service communication. Payment gateways like Stripe, communication APIs like Twilio or WhatsApp Business, and version control platforms like GitHub rely on HTTP POST webhooks to notify your backend of critical real-world events. When an invoice is paid, a subscription is upgraded, or an external AI model finishes a batch job, an incoming webhook notifies your application to execute business side effects.

However, treating a webhook endpoint like a standard synchronous REST route is an architectural anti-pattern. Webhooks operate across untrusted public networks where network drops, server restarts, downstream database delays, and provider retries are daily occurrences. If your handler takes longer than 2–3 seconds to respond, providers assume delivery failed and trigger automatic retry storms. Without strict idempotency controls and asynchronous background queues, your application will process duplicate events, double-credit user accounts, or exhaust its database connection pool.

In this comprehensive guide, we engineer an enterprise-grade webhook ingestion architecture in Node.js and TypeScript. We will cover raw body preservation for HMAC-SHA256 signature verification, immediate 202 Accepted acknowledgment, PostgreSQL idempotency tracking, background queue processing with BullMQ and Redis, and exponential backoff with jitter retry strategies. For background on queuing infrastructure, check our guide on Redis caching and scaling in Node.js and our overview of Node.js API security best practices.

Why Webhooks Fail in Production

Before implementing defensive controls, let us examine the common failure modes of naive webhook handlers:

  • Provider Timeouts: Most third-party platforms enforce strict HTTP timeouts (e.g., Stripe times out after 10–20 seconds; GitHub after 10 seconds; Slack after 3 seconds). If your handler performs database writes, sends customer emails, or triggers AI generations synchronously inside the HTTP handler, it will periodically time out, triggering repeated delivery attempts.
  • Duplicate Deliveries: Webhook providers guarantee at-least-once delivery, not exactly-once delivery. Network latency or packet drops on acknowledgment responses mean your server will inevitably receive the exact same event multiple times.
  • Out-of-Order Delivery: There is no guarantee that an order.created event will arrive before an order.fulfilled event. If network congestion delays the first event, the second may be processed first.
  • JSON Mutation Bugs: Standard Express middleware (such as express.json()) parses and serializes request bodies into JavaScript objects. This alters whitespace, key ordering, or Unicode characters, completely invalidating cryptographic signature checks.

Step 1: Cryptographic Signature Verification with Raw Bodies

Never process an incoming webhook without verifying its cryptographic signature. A publicly exposed webhook URL can be called by anyone; signature verification guarantees that the payload originated from the authentic provider and was not altered in transit.

Signature verification uses Hash-based Message Authentication Codes (HMAC-SHA256). The provider hashes the raw, unparsed payload using a shared secret and transmits the digest in an HTTP header (e.g., Stripe-Signature or X-Hub-Signature-256). Your server must compute the exact same hash using its private signing secret and compare them.

Preserving the Raw Buffer in Express

To verify the signature, you must have access to the exact raw request bytes before any JSON parsing occurs. Configure Express to capture the raw buffer:

import express from "express";

const app = express();

// Capture raw body buffer specifically for the webhook endpoint
app.use(
  "/api/webhooks",
  express.raw({
    type: "application/json",
    limit: "2mb" // Strictly bound body size to prevent memory exhaustion attacks
  })
);

// Standard JSON parsing for the rest of your application routes
app.use(express.json());

Verifying Signatures with Constant-Time Comparison

When comparing cryptographic hashes, never use the standard equality operator (===). String comparison operators terminate early upon finding the first mismatched character, creating a timing attack vulnerability that allows attackers to iteratively guess valid signatures. Always use Node.js's native crypto.timingSafeEqual():

import crypto from "crypto";

interface VerificationResult {
  isValid: boolean;
  error?: string;
}

export function verifyWebhookSignature(
  rawPayload: Buffer,
  signatureHeader: string | undefined,
  secret: string,
  toleranceSeconds: number = 300
): VerificationResult {
  if (!signatureHeader) {
    return { isValid: false, error: "Missing signature header" };
  }

  // Parse header components: e.g., t=1729681200,v1=9f8a7c...
  const parts = signatureHeader.split(",").reduce((acc, part) => {
    const [key, val] = part.split("=");
    if (key && val) acc[key.trim()] = val.trim();
    return acc;
  }, {} as Record<string, string>);

  const timestamp = parts["t"];
  const expectedSignature = parts["v1"];

  if (!timestamp || !expectedSignature) {
    return { isValid: false, error: "Malformed signature header components" };
  }

  // 1. Prevent Replay Attacks: Enforce maximum timestamp age (e.g., 5 minutes)
  const eventTime = parseInt(timestamp, 10);
  const currentTime = Math.floor(Date.now() / 1000);
  if (Math.abs(currentTime - eventTime) > toleranceSeconds) {
    return { isValid: false, error: "Timestamp outside tolerance window (replay attack)" };
  }

  // 2. Compute HMAC-SHA256 signature
  const signedPayload = `${timestamp}.${rawPayload.toString("utf8")}`;
  const computedSignature = crypto
    .createHmac("sha256", secret)
    .update(signedPayload, "utf8")
    .digest("hex");

  // 3. Constant-Time Buffer Comparison
  const computedBuf = Buffer.from(computedSignature, "hex");
  const expectedBuf = Buffer.from(expectedSignature, "hex");

  if (computedBuf.length !== expectedBuf.length) {
    return { isValid: false, error: "Signature length mismatch" };
  }

  const isMatch = crypto.timingSafeEqual(computedBuf, expectedBuf);
  return {
    isValid: isMatch,
    error: isMatch ? undefined : "Invalid cryptographic signature"
  };
}

Step 2: The Two-Phase Ingestion Architecture

To eliminate provider timeouts and protect system availability, decouple webhook ingestion into two distinct phases:

  1. Synchronous Ingestion Phase (< 200ms):
    • Verify signature and timestamp.
    • Extract the unique external event ID (e.g., evt_3Mz4...).
    • Store the event payload in PostgreSQL with status received.
    • Push a background processing job onto a Redis-backed queue.
    • Immediately return HTTP 202 Accepted (or 200 OK) to the provider.
  2. Asynchronous Processing Phase (Workers):
    • A worker picks up the job from the queue.
    • Acquires an idempotency lock on the event ID.
    • Executes domain mutations (updates user subscriptions, charges cards, provisions credits).
    • Updates event status to processed.
    • Handles transient errors via exponential backoff or dead-letter queues.

Step 3: Database Idempotency Schema in PostgreSQL

Idempotency ensures that processing an event multiple times produces the exact same outcome as processing it once. Create a dedicated webhook_events table in PostgreSQL with strict uniqueness constraints:

CREATE TYPE webhook_status AS ENUM ('received', 'processing', 'completed', 'failed');

CREATE TABLE webhook_events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  provider text NOT NULL, -- e.g., 'stripe', 'whatsapp', 'github'
  event_id text NOT NULL, -- Provider's unique event identifier (e.g., evt_1092)
  event_type text NOT NULL, -- e.g., 'invoice.payment_succeeded'
  payload jsonb NOT NULL,
  status webhook_status NOT NULL DEFAULT 'received',
  attempts integer NOT NULL DEFAULT 0,
  last_error text,
  received_at timestamptz NOT NULL DEFAULT now(),
  processed_at timestamptz,
  -- Crucial unique index to guarantee at-most-once registration
  CONSTRAINT uq_webhook_provider_event UNIQUE (provider, event_id)
);

CREATE INDEX idx_webhook_status_created ON webhook_events (status, received_at);

When an incoming webhook arrives, use an ON CONFLICT DO NOTHING query. If the row already exists, the database immediately rejects the duplicate write without error, allowing the HTTP endpoint to acknowledge the provider safely:

async function recordIncomingEvent(
  provider: string,
  eventId: string,
  eventType: string,
  payload: any
): Promise<{ isDuplicate: boolean; id?: string }> {
  const sql = `
    INSERT INTO webhook_events (provider, event_id, event_type, payload)
    VALUES ($1, $2, $3, $4)
    ON CONFLICT (provider, event_id) DO NOTHING
    RETURNING id;
  `;
  const result = await pool.query(sql, [provider, eventId, eventType, JSON.stringify(payload)]);

  if (result.rowCount === 0) {
    return { isDuplicate: true };
  }
  return { isDuplicate: false, id: result.rows[0].id };
}

Step 4: Background Queue Processing with BullMQ

BullMQ is the industry-standard Redis-backed queue library for Node.js. It provides native support for delayed jobs, exponential retries, parent-child job workflows, and dead-letter queue isolation.

Install BullMQ:

npm install bullmq

Configuring the Producer Queue

Configure the ingestion queue with explicit retry policies and unique job IDs to prevent duplicate queuing:

import { Queue } from "bullmq";
import { redisConnection } from "./redis.js";

export const webhookQueue = new Queue("incoming-webhooks", {
  connection: redisConnection,
  defaultJobOptions: {
    // Retry up to 5 times on unhandled exceptions
    attempts: 5,
    backoff: {
      type: "exponential",
      delay: 2000 // Initial backoff: 2s, 4s, 8s, 16s, 32s
    },
    // Keep completed jobs for 24 hours for audit trails; keep failed jobs for debugging
    removeOnComplete: { age: 86400, count: 5000 },
    removeOnFail: { age: 604800, count: 10000 }
  }
});

// Enqueue the verified webhook
export async function enqueueWebhook(provider: string, eventId: string, eventType: string) {
  await webhookQueue.add(
    eventType,
    { provider, eventId },
    {
      // Using provider eventId as BullMQ jobId prevents duplicate jobs in the queue!
      jobId: `${provider}:${eventId}`
    }
  );
}

Building the Dedicated Worker

In a separate worker process, consume and process jobs with transaction-isolated idempotency:

import { Worker, Job } from "bullmq";
import { redisConnection } from "./redis.js";
import { pool } from "./db.js";

interface WebhookJobData {
  provider: string;
  eventId: string;
}

export const webhookWorker = new Worker<WebhookJobData>(
  "incoming-webhooks",
  async (job: Job<WebhookJobData>) => {
    const { provider, eventId } = job.data;

    const client = await pool.connect();
    try {
      await client.query("BEGIN");

      // Lock the event row for update to prevent concurrent worker execution
      const eventRes = await client.query(
        `SELECT id, event_type, payload, status 
         FROM webhook_events 
         WHERE provider = $1 AND event_id = $2 
         FOR UPDATE`,
        [provider, eventId]
      );

      if (eventRes.rowCount === 0) {
        throw new Error(`Webhook record not found for ${provider}:${eventId}`);
      }

      const event = eventRes.rows[0];

      // If already processed, exit cleanly (idempotency guarantee)
      if (event.status === "completed") {
        await client.query("COMMIT");
        return;
      }

      // Mark status as processing
      await client.query(
        `UPDATE webhook_events 
         SET status = 'processing', attempts = attempts + 1 
         WHERE id = $1`,
        [event.id]
      );

      // Execute domain business logic based on event type
      await processDomainEvent(event.event_type, event.payload, client);

      // Mark completed
      await client.query(
        `UPDATE webhook_events 
         SET status = 'completed', processed_at = now() 
         WHERE id = $1`,
        [event.id]
      );

      await client.query("COMMIT");
    } catch (error: any) {
      await client.query("ROLLBACK");
      // Record error on the event record
      await pool.query(
        `UPDATE webhook_events 
         SET last_error = $1 
         WHERE provider = $2 AND event_id = $3`,
        [error.message, provider, eventId]
      );
      // Re-throw so BullMQ triggers exponential backoff retry!
      throw error;
    } finally {
      client.release();
    }
  },
  {
    connection: redisConnection,
    concurrency: 10 // Process up to 10 webhooks concurrently per worker
  }
);

Step 5: Exponential Backoff, Jitter, and Dead-Letter Queues (DLQ)

When a worker fails due to an external outage (such as a database deadlock or third-party API 500 error), retrying immediately overwhelms the struggling service. Exponential backoff doubles the delay between successive attempts.

Furthermore, in large distributed fleets, add full jitter to randomize retry timestamps. Without jitter, all workers that failed at time T will retry together at time T + delay, re-creating the initial traffic spike.

Handling the Dead-Letter Queue (DLQ)

If an event fails after exhausting all 5 retry attempts, BullMQ marks the job as failed. In webhook architecture, this is your Dead-Letter state. Implement an automated alerting hook and an administrative replay API:

webhookWorker.on("failed", async (job, err) => {
  if (job && job.attemptsMade >= (job.opts.attempts || 5)) {
    console.error(
      `CRITICAL: Webhook ${job.data.provider}:${job.data.eventId} permanently failed!`,
      err.message
    );
    // Send PagerDuty / Slack alert to on-call engineering team
    await sendOpsAlert({
      title: "Webhook Permanently Failed",
      details: { jobId: job.id, error: err.message, payload: job.data }
    });
  }
});

// Admin endpoint to manually re-queue fixed dead-letter webhooks
app.post("/admin/webhooks/replay/:id", requireAdmin, async (req, res) => {
  const { id } = req.params;
  const event = await pool.query("SELECT * FROM webhook_events WHERE id = $1", [id]);
  
  if (event.rowCount === 0) {
    return res.status(404).json({ error: "Event not found" });
  }

  await pool.query("UPDATE webhook_events SET status = 'received' WHERE id = $1", [id]);
  await enqueueWebhook(event.rows[0].provider, event.rows[0].event_id, event.rows[0].event_type);

  res.json({ message: "Webhook successfully re-enqueued for execution" });
});

Step 6: Assembling the Express Endpoint

Now, combine all controls into a clean, unified Express route:

app.post("/api/webhooks/stripe", async (req, res) => {
  const rawBody = req.body as Buffer;
  const signature = req.headers["stripe-signature"] as string;

  // 1. Verify HMAC Signature
  const verification = verifyWebhookSignature(
    rawBody,
    signature,
    process.env.STRIPE_WEBHOOK_SECRET!
  );

  if (!verification.isValid) {
    console.warn("Rejected unauthorized webhook:", verification.error);
    return res.status(400).send(`Webhook Error: ${verification.error}`);
  }

  // 2. Parse JSON safely now that authenticity is proven
  let event: any;
  try {
    event = JSON.parse(rawBody.toString("utf8"));
  } catch (err) {
    return res.status(400).send("Malformed JSON body");
  }

  // 3. Persist Event Idempotently in PostgreSQL
  const { isDuplicate } = await recordIncomingEvent(
    "stripe",
    event.id,
    event.type,
    event
  );

  if (isDuplicate) {
    // Acknowledge duplicate immediately without re-enqueuing
    return res.status(200).json({ received: true, note: "duplicate" });
  }

  // 4. Enqueue to BullMQ for Asynchronous Background Processing
  await enqueueWebhook("stripe", event.id, event.type);

  // 5. Acknowledge Provider within 150ms
  return res.status(202).json({ received: true });
});

Production Best Practices Checklist

  • Always verify cryptographic signatures against the raw body buffer using constant-time comparison.
  • Acknowledge webhooks with HTTP 200 or 202 in under 200ms before triggering business logic.
  • Store incoming event IDs in PostgreSQL with a unique constraint to guarantee idempotency.
  • Offload domain side effects to a Redis-backed queue like BullMQ.
  • Configure exponential backoff with randomized jitter on all background worker retries.
  • Set up alerting on dead-letter queue failures and provide an administrative replay endpoint.

Frequently Asked Questions

Why should I return HTTP 202 instead of HTTP 200?

HTTP 202 Accepted explicitly signals to clients that the request has been received and validated, but processing has not yet concluded. However, some older providers require an exact 200 OK. Both are acceptable as long as response time remains under 200ms.

How do I test webhooks on my local machine?

Use official CLI tools like the stripe listen --forward-to localhost:3000/api/webhooks/stripe or Ngrok tunnels. The official Stripe CLI automatically creates a temporary local signing secret for signature verification.

What if my database is down when a webhook arrives?

If your database is completely unreachable during ingestion, return an HTTP 503 Service Unavailable. The provider will recognize the transient failure and automatically retry delivery according to its published retry schedule.
